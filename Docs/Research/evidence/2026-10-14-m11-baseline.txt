First measured change (same machine, fixture and release build): seeking now skips
non-reference frames that end before the target (AVDISCARD_NONREF), redoing the seek without
skipping if a skipped frame was the one on screen. --m4-seek-audit baseline_1080p60.mp4 30,
two runs each, hardware decode:
  before: first frame p50 198.9 / 208.4 ms, p95 392.0 / 378.4 ms, max 436.8 / 435.6 ms
  after:  first frame p50 152.5 / 160.5 ms, p95 292.1 / 280.8 ms, max 324.3 / 368.6 ms
  (about -23 % p50, -26 % p95). Software decode after the change: p50 109 ms, p95 194 ms,
  faster than VA-API for seeks on this GOP (worth a look: per-frame hardware latency).
Exactness: tests/media seeks every frame of h264_vfr.mkv, h264_29.97fps.mp4 and hevc_10bit.mp4
at its time and mid-gap; skipping on pts <= target without the redo gives 38/28/28 wrong frames.

Second measured change: seeking during playback with software decode on 4K. Fixture (not
committed): ffmpeg -f lavfi -i testsrc2=size=3840x2160:rate=30:duration=20 -f lavfi -i
sine=frequency=440:sample_rate=48000:duration=20 -c:v libx265 -preset ultrafast
-pix_fmt yuv420p10le -c:a aac -shortest hevc4k10.mp4  (GOP 8.3 s, B-frames).
--m4-seek-audit hevc4k10.mp4 20 (seeks while playing; "UI blocked" is the restart on the UI
thread, which joins the video producer):
  software, before: UI blocked p50 173 ms, p95 799 ms; first frame p50 228 ms; 14 of 20 seeks
                    without a frame in 500 ms
  software, after:  UI blocked p50 25 ms, p95 77 ms; first frame p50 223 ms; 13 of 20 without
  hardware, after:  UI blocked p50 3.3 ms, p95 8.1 ms; first frame p50 203 ms, 0 without
The producer's seek decoded forward up to a whole GOP inside VideoDecoder::next() without
looking at cancellation, so stop() waited for it; the decoder now checks an interrupt between
decoded frames, the scheduler ties it to its job's cancellation, and FrameSource drops a stream
stopped mid-seek. Software decode stays too slow for 4K HEVC seeks (decode throughput), so the
paused/scrub policy is not switched to software despite its faster 1080p H.264 seeks.

Third change: scrubbing the paused viewer (software decode, the default on GPUs not yet
validated for hardware decode). A temporary variant of --m4-seek-audit (not committed) paused
the editor and issued bursts of five seeks ~15 ms apart, timing the last one's frame;
baseline_1080p60.mp4, 15 bursts, two runs each:
  before: final frame p50 190.8 / 189.2 ms, p95 285.8 / 295.9 ms
  after:  final frame p50 114.9 / 122.0 ms, p95 206.8 / 208.2 ms
A newer paused-viewer request now stops the frame in flight between decoded frames (the same
decoder interrupt), instead of letting a superseded seek finish its GOP of catch-up.
tests/app/test_frame_source_interrupt.cpp scrubs a 10 s one-keyframe clip; treating the
superseded frame as an error makes it fail.
